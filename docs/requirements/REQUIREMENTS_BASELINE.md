# ScryX — базовая спецификация требований

Снимок от 2026-11-06. Путь в репозитории: `docs/requirements/REQUIREMENTS_BASELINE.md`.
Это рабочая базовая версия требований проекта. Язык реализации — Python.

Для разработки используется этот реестр и согласованные изменения. Неразрешённые противоречия сохраняются в разделе открытых вопросов до согласования.

## Границы и архитектура

- Система выполняет технический контроль секвенций перед композитингом. Очередь 1 — автономная работа. Очередь 2 — интеграция со студией. Возможность вызова CLI внешним скриптом входит в очередь 1. Автоматический запуск по событиям — ФТ-20, очередь 2.
- Один процесс на экземпляр приложения в очереди 1, режимы GUI и CLI используют общую прикладную логику. Пакеты `ui`, `cli` → `core` → `domain`, `storage`. SQLite доступна через `Repository`. Чтение файлов и проверка выполняются в фоне, результаты передаются через сигналы и слоты Qt. Движок расширяется реализациями абстрактного класса `Check`.
- Исходные кадры доступны только для чтения. Локальные данные — в каталоге пользователя, экспорт — в выбранный каталог. Во второй очереди обмен в локальной сети через общий каталог и HTTP/JSON, с идентификацией и разграничением доступа. Повреждённый кадр отмечается и пропускается, проверка остальных продолжается. При проблемах с сетевым каталогом применяется ожидание 10 с.
- D1 — `sequence`, `frame`; D2 — `check_profile`, `expected_aov`; D3 — `check_run`, `defect_type`, `defect`. Схема в 3НФ, PK/FK/AK и CHECK, `PRAGMA foreign_keys`, миграции с сохранением данных. Номер отсутствующего кадра в дефекте хранится без FK на `frame`. Кадры остаются во внешних файлах.
- Журнал с временем, уровнем, подсистемой и сообщением, ограничение 10 МБ и три последних файла. Транзакции SQLite и WAL, сохранение частичных результатов при аварии, временный файл с переименованием при записи отчёта. Сбой записи SQLite — откат, экспорт JSON и сообщение пользователю.
- Поддержка секвенций не менее 10 000 кадров, разрешения не менее 8192×8192, не менее 64 каналов, не менее 10 000 запусков. Линейный рост времени по числу кадров и пикселей. Не менее 100 последовательных проверок по 240 кадров без аварии, восстановление не более 1 минуты. Для этих пунктов в программе испытаний нет полного набора отдельных сценариев.
- Английский интерфейс с переключением на русский, термины и имена каналов сохраняются, CLI и коды дефектов на английском, текст UTF-8. Статусы дублируются значком и текстом, предусмотрены горячие клавиши, экран от 1366×768 и масштабирование 100–200 %.
- Рекомендуемая конфигурация от 4 ядер, 16 ГБ, SSD. Минимум 2 ядра x86-64 или ARM64, 8 ГБ. Для замеров — `time.perf_counter`, не менее пяти повторов и медиана. Для детекторов — эталонные секвенции с известными дефектами.
- Установка до 5 минут без прав администратора. Windows — установщик или переносная сборка. Ubuntu и macOS — пакет Python или переносная сборка. Требуемые платформы в НФТ-15. Реальная совместимость выбранных сборок ещё не подтверждена.
- Приёмка первой очереди: все ИСП-01–ИСП-14 со статусом «соответствует», проектная и пользовательская документация, замечания опытной эксплуатации устранены или согласованы. При отказе — исправление и повтор затронутых испытаний.

## Данные и интерфейсы для реализации

- Шаблоны `name.####.ext` и `name_####.ext`. Пропуски вычисляются как разность ожидаемых и найденных номеров. Источник ожидаемых границ, обработка смешанных секвенций и приоритет диапазонов требуют уточнения.
- Для читаемых кадров проверяются AOV без учёта регистра, NaN/Inf по каналам, отрицательные значения ниже −10⁻⁶ с исключениями по профилю, чёрный кадр по максимуму RGB ≤10⁻⁶. Формулы экспозиции и гаммы применяются к отображаемой копии. Векторная обработка пикселей — NumPy float32. Результат просмотра исходных значений регулирует ФТ-04.
- Коды `MISSING_FRAME`, `CORRUPTED_FILE`, `MISSING_AOV`, `NAN_INF`, `NEGATIVE`, `BLACK_FRAME`. Состояние выполнения `running/completed/failed` отделено от результата проверки `PASSED/WARNING/FAILED`. Для завершённого анализа результат вычисляется по наличию ошибок и предупреждений.
- `scryx check <путь> [параметры]`, `--profile <имя>`, `--frames <A-B>`, `--json <файл>`, `--html <файл>`, `--quiet`. Также `scryx profile list/export/import`. Без `--json` указан вывод JSON в stdout. Код 0 означает отсутствие дефектов уровня error, код 1 — наличие error, код 2 — ошибку запуска. Уточнения по диагностике и ошибкам выполнения см. OPEN-05.
- JSON отчёта — пример формата, включён в машинный блок. `scryx_version` относится к версии приложения, `report_format` — к формату обмена. Читаемый экспорт — HTML с таблицей и миниатюрами дефектных кадров. Пример JSON не задаёт исчерпывающую JSON Schema.

## Стек и проверка поставки

| Компонент | Основание и назначение | Что нужно подтвердить перед фиксацией версий |
|---|---|---|
| Python | НФТ-17: 3.11 / 3.11+ | Конкретный runtime и ABI для каждой целевой сборки. |
| PySide6 / Qt 6 | GUI, Qt signals/slots и Qt Linguist | Доступность сборок, запуск Qt-плагинов в чистой ОС, соблюдение условий распространения по НФТ-23. |
| OpenImageIO / OpenEXR | Чтение EXR, PNG, TIFF, включая EXR multipart и перечисленные виды сжатия | Доступность wheels либо воспроизводимой сборки, версии нативных библиотек, декодирование эталонов. OpenEXR указан в стеке, необходимость отдельного Python-пакета определяется реализацией. |
| NumPy | Векторные вычисления над пикселями | Совместимость с runtime и нативными расширениями, точность и производительность. |
| SQLite | Локальные данные и миграции | Версия SQLite в каждой сборке, FK, транзакции, восстановление и backup. |
| pytest | Тесты детекторов и проверка CLI | Отдельная зависимость разработки и воспроизводимый прогон тестов. |
| OpenColorIO | Цветоуправление, очередь 2 | Версию и интеграцию согласовать при проектировании второй очереди. |

Проверка совместимости — отдельный шаг. Точные версии, способ упаковки и успешная установка на целевых ОС не подтверждены. Редакцию VFX Reference Platform и совместимость требуется проверить по OPEN-06.

Предлагаемый порядок проверки, пока без статуса требования:

1. Определить матрицу сборок для Windows 10/11 64-bit, Ubuntu 22.04+ и macOS 12+. Уточнить поддерживаемые сочетания ОС и архитектур x86-64/ARM64.
2. Сверить ограничения Python, PySide6, OIIO и NumPy, нативные зависимости и минимальные версии ОС.
3. Собрать и установить дистрибутивы на чистых целевых ОС без прав администратора. Проверить запуск GUI и CLI без сети, локальное сохранение, OpenEXR multipart, PNG/TIFF, экспорт, время установки и ИСП-13. Сохранить логи и версии фактических сборок.
4. После подтверждения зафиксировать версии runtime и зависимостей, артефакты сборки и состав лицензий. Если утверждённые условия одновременно невыполнимы, согласовать новые условия до изменения требований или критериев.

| OPEN-09 | ФТ-07 и ИСП-05: пропуск на краю диапазона невозможно восстановить только из списка имеющихся файлов. Неясен приоритет диапазона профиля и `--frames`. | Согласовать источник ожидаемых границ, правила приоритета и граничные эталоны. |

| OPEN-11 | Ряд критериев не покрыт явно отдельными испытаниями: время установки, восстановление после аварии, 100 запусков, предельные объёмы. ИСП-14 проверяет самостоятельность после обучения, но не считает действия для НФТ-11. | Добавить проверочные сценарии к программе испытаний после согласования. Существующие ИСП сохранить. |
| OPEN-12 | Очередь 2: RGB > alpha не является универсальным признаком ошибки premultiplied HDR. Формула может пометить корректные световые значения. | Перед реализацией ФТ-12 согласовать область применимости, допуски и эталоны. |
| OPEN-13 | В концепции интерфейса предусмотрена подсветка дефектных пикселей. Модель данных хранит число пикселей и канал, без координат или маски. | Уточнить обязательность подсветки и способ получения маски. ФТ-10 уже покрывается данными о кадре, канале и количестве. |

Записи OPEN остаются открытыми. Предложения не меняют требования до согласования.

## Правила изменений

- Если меняется внутреннее устройство кода при сохранении наблюдаемого поведения и всех ограничений требований, это изменение реализации. Изменение формата отчёта, кода выхода, порога, ОС, состава функций, очереди или условия приёмки — изменение требования.
- Для изменения требования записать затронутые ID, исходное и предлагаемое значения, причину, влияние на диаграммы, классы, экраны и испытания, решение владельца проекта. После принятия обновить журнал решений и снимок требований.
