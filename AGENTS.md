# ScryX — инструкции для Codex CLI

## Требования

- Работай из корня репозитория ScryX. Сохраняй существующие спайки, тестовые данные и Git-историю.
- Перед проектированием прочитай `docs/requirements/REQUIREMENTS_BASELINE.md` и найди связанные ФТ, НФТ и ИСП. Реестр требований и согласованные изменения имеют приоритет. Паспорт и спайки дают исторический контекст.
- При расхождении формулировок приведи ID, источники и последствия. Изменение объёма, порога, платформы, формата, кода выхода или приёмки требует отдельного согласования. Записывай принятые решения с датой и связанными ID.
- GUI и CLI используют общую логику проверки. Исходные кадры доступны только для чтения. Первая очередь работает автономно. Добавляй модули по мере появления конкретной задачи.

## Работаем вместе

- Веди одну активную задачу. Дай цель и связанные ФТ/НФТ, ожидаемый результат, нужные знания и минимум теории, план самостоятельной реализации, тесты и крайние случаи, критерии готовности и одно упражнение.
- Дай разработчику первую попытку. Помогай по ступеням: подсказка, пример, частичная реализация. Полное решение давай по запросу. Рутинные правки документации и согласованные проверки можешь выполнить сам.
- После блока коротко проверь понимание. В `LEARNING.md` фиксируй со слов разработчика один из статусов: разобрался самостоятельно, реализовал с ИИ и понимаю, делегировал ИИ и пока не разобрался.

## Проверки и Git

- Различай написанный, запущенный и проверенный код. Перед завершением посмотри `git status --short`, `git diff`, `git diff --cached` и `git diff --check`. Прогони подходящие тесты по актуальной инструкции README. Укажи команды, результаты и ограничения. Отмечай готовность после выполнения критериев.
- Git используй для чтения статуса, истории и diff. Коммиты, push, merge, rebase, reset и изменения индекса оставляй разработчику. Предлагай границы коммита и сообщение. Береги его локальные изменения.

## Документы

- `README.md` обновляй, когда меняются проверенные команды, структура или возможности. `docs/README.md` поддерживай как навигацию по документации.
- `CHANGELOG.md` обновляй в Unreleased для заметных пользователю изменений. Принятые технические решения записывай в `docs/decisions.md` с причиной и ссылками на требования.
- `LEARNING.md` обновляй после учебного блока. Записывай освоенное, пробелы и короткое упражнение. Историю спайков и исследований оставляй в `docs/project_journal.md`.
- Обновляй затронутые документы в рамках текущей задачи. Снимок требований меняй после согласования изменения. Отвечай разработчику по-русски, коротко и по делу.
